# Task: The studio requires an account

## 1. Problem / requested change

The owner, after the first successful deployment: "quiero ahora integrar supabase y
autentificacion". Asked how far to take it, they chose the sign-in gate first and user-owned
designs as a separate task afterwards. Evidence: INTENT.

## 2. Current behavior

- `web.spec.md` records "Authentication approach is undecided" (UNKNOWN) while its security section
  claims the tier "enforces authentication and authorization on every route". It enforces none.
  Evidence: OBSERVED.
- `POST /api/consultation`, `/api/generate` and `/api/media` accept any caller. Each spends money:
  a live model call, image generation, a moderation call. Evidence: OBSERVED.
- The studio is now reachable on a real domain (TASK-0043/0044), so this is exposure, not theory.
  Evidence: OBSERVED.

## 7. Requirements

- **REQ-001** — Every route that spends money or reads stored work refuses a caller without an
  account, and reaches neither the worker nor a model when refusing.
- **REQ-002** — Sign-in exchanges credentials for `HttpOnly`, `SameSite=strict` cookies, server
  side; the password goes nowhere but Supabase.
- **REQ-003** — A wrong password and an unknown address are indistinguishable to the caller.
- **REQ-004** — A deployment with no authentication configured refuses everyone (503).
- **REQ-005** — An expired access token is renewed from the refresh token and the renewed pair is
  re-issued on the same response.
- **REQ-006** — A visitor without a session lands on the sign-in page rather than a studio that
  fails on every action; a forged cookie gets no further than the HTML shell.
- **REQ-007** — There is no sign-up.

## 8. Acceptance criteria

- **AC-001** — Unauthenticated POSTs to consultation, generate and media return 401, and no
  outbound call is made.
- **AC-002** — Unauthenticated reads of the consultation, job history, media and deletion do not
  return 200.
- **AC-003** — Sign-in sets both cookies with `HttpOnly` and `SameSite=strict`, and the body
  carries nothing about the account.
- **AC-004** — An unknown address and a wrong password produce identical responses, with no cookie.
- **AC-005** — Cross-site sign-in is refused (403); an incomplete one is 400; an unreachable
  Supabase is 503, not a refusal.
- **AC-006** — With `SUPABASE_URL`/`SUPABASE_ANON_KEY` unset, a route returns 503.
- **AC-007** — A stale access token with a good refresh token yields 200 and re-issued cookies; a
  revoked refresh token yields 401.
- **AC-008** — Live: `/` and `/probar` redirect to `/entrar`; `/entrar` serves; the API refuses
  both an absent and a forged cookie.

## 15. Decision log

- **DEC-001** — ADR-0021: Supabase is asked who a token belongs to rather than verifying it here.
  No signing secret in this deployment, no token parsing in our code.
- **DEC-002** — The middleware checks only for a cookie's presence. It is a courtesy that keeps
  strangers off the pages at no latency cost, not the boundary; the API is the boundary. Verified
  by the forged-cookie case in AC-008.
- **DEC-003** — Route tests drive the real guard instead of mocking it, so each route proves it
  refuses a stranger. The cost is that every existing test had to present an account.
- **DEC-004** — `GET /api/consultation` previously answered 200 with `session: null` for any
  failure, including an unauthenticated one. Separated: no account is 401, no consultation is 200.
  The page redirects on the 401, which is how a stale cookie resolves itself.
- **DEC-005** — Only the anon key. Nothing here acts as an administrator, so the service-role key
  is not present and cannot leak.
- **DEC-006** — Designs remain owned by the studio session, not the account. Deliberately left to
  TASK-0046: moving ownership touches the worker's scoping and the cascade-deletion invariant.
