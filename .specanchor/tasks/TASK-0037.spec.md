# Task: The server refuses to generate from a brief nobody accepted

## 1. Problem / requested change

Phase 0, item 3 of the competitive plan. TASK-0029 gated generation on accepting the master
brief, but only in the interface (TASK-0029/DEC-003): a caller bypassing it could still submit.

## 2. Current behavior

- Acceptance is a signature held in React state in `page.tsx`. Evidence: OBSERVED.
- `POST /api/generate` checks age, consent, reference review and brief completeness, never
  acceptance. `generate/route.test.ts` generates without accepting and expects 202.
  Evidence: OBSERVED.
- Since TASK-0033 the consultation orchestrator calls Claude live, so any accept action routed
  through it would cost a model call and could rewrite slots. Evidence: OBSERVED.

## 3. Desired behavior

The server records what the client accepted and refuses a new generation unless the brief it
would send still matches that acceptance.

## 7. Requirements

- **REQ-001** — One shared `briefSignature` function, used by client and server, so both compute
  the same value from the same brief.
- **REQ-002** — `accept_brief` recomputes the brief from server state, refuses an incomplete brief
  (422) and a signature that differs from what the client read (409), and records the server's
  signature. It never runs the orchestrator.
- **REQ-003** — `POST /api/generate` refuses a new design (409) unless the stored acceptance
  matches the brief as it now stands. A change after acceptance therefore withdraws it.
- **REQ-004** — The interface marks the brief accepted only after the server confirms.

## 8. Acceptance criteria

- **AC-001** — Generating without accepting returns 409 and submits nothing to the worker.
- **AC-002** — Accepting with a stale signature returns 409; accepting an incomplete brief 422.
- **AC-003** — Accepting then generating returns 202 with the server brief.
- **AC-004** — Changing a preference after accepting makes generation return 409 again.
- **AC-005** — Accepting makes no model call.
- **AC-006** — Removing the guard makes the tests fail.

## 15. Decision log

- **DEC-001** — Acceptance returns before the orchestrator. Since TASK-0033 the orchestrator calls
  Claude live, so routing acceptance through it would cost a model call and could rewrite the
  slots the client just agreed to.
- **DEC-002** — The client sends the signature it read and the server refuses a mismatch rather
  than silently storing its own. Otherwise a client that accepted a stale view would be recorded
  as agreeing to a brief it never saw.
- **DEC-003** — Edits to an already accepted design do not pass through this guard. They refine a
  design the client has seen, and are gated separately by age and consent.
- **DEC-004** — The first test for AC-004 passed for the wrong reason: its session never reached
  `ready_to_generate`, so the earlier readiness guard answered with 422 before this one ran. The
  assertion moved into the flow that does reach readiness, and now also checks the refusal message,
  proving it is this guard that refuses.
