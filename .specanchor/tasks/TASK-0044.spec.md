# Task: Deploy through Coolify instead of our own proxy

## 1. Problem / requested change

The owner reported what the VM actually runs: "esta VM ya tiene instalado Coolify, Supabase y N8N".
TASK-0043 was written before that was known. Evidence: INTENT (owner statement).

## 2. Current behavior

- `infra/docker-compose.yml` publishes `80:80`, `443:443` and `443:443/udp` for its own Caddy
  service. Evidence: OBSERVED.
- `infra/Dockerfile.caddy` compiles a DNS provider module and `infra/Caddyfile` configures a DNS-01
  challenge, duplicating what Coolify already does. Evidence: OBSERVED.
- The runbook walks through installing Docker and running `docker compose up -d` by hand. Evidence:
  OBSERVED.

**This would not have started.** Coolify owns 80 and 443 on that host; a second service binding
them fails at container start. TASK-0043's configuration was coherent but written against the wrong
host, and its images were never built, so nothing caught it.

## 3. Desired behavior

Coolify builds and runs the two services, terminates TLS and holds the secrets. The repository
carries only what Coolify cannot infer.

## 7. Requirements

- **REQ-001** — No service binds a host port; the web app is exposed on the compose network for
  Coolify's proxy to route to.
- **REQ-002** — Our proxy layer is removed, not left dormant: no `Caddyfile`, no `Dockerfile.caddy`.
- **REQ-003** — Secrets come from Coolify's environment panel rather than an `.env` file on disk,
  and the compose file fails loudly when a required one is absent.
- **REQ-004** — The runbook describes the Coolify path, and still states the no-authentication
  exposure before its first step.
- **REQ-005** — The worker stays a single replica, unreachable from outside, with its state on a
  named volume.

## 8. Acceptance criteria

- **AC-001** — The compose file declares exactly `worker` and `web`, neither has `ports:`, and
  `web` has `expose:`.
- **AC-002** — Neither `infra/Caddyfile` nor `infra/Dockerfile.caddy` exists.
- **AC-003** — The compose file references the domain variable Coolify fills for the web service.
- **AC-004** — The runbook's exposure warning precedes its first step.
- **AC-005** — The committed template still holds no credential-shaped value.
- **AC-006** — The worker keeps `replicas: 1`, `TATTOO_DATA_DIR` on the volume, and the volume mount.

## 15. Decision log

- **DEC-001** — Amends ADR-0020 rather than replacing it. The decision that survives is the one that
  mattered: one self-hosted node on the owner's hardware, which is what settles residency. Only the
  proxy layer changes, from our Caddy to Coolify's.
- **DEC-002** — The Caddy files are deleted rather than kept for a hypothetical non-Coolify host.
  Two proxy configurations in one tree is an invitation to deploy the wrong one, and the deleted
  version stays in git history if it is ever wanted.
- **DEC-003** — Required secrets use `${VAR:?message}` so a missing one fails the deploy with a
  named variable, instead of starting a container that 503s at the first generation.
- **DEC-004** — Supabase is installed on that VM but the studio still does not use it. Storage
  remains SQLite plus the encrypted file store; migrating is its own task, as decided in
  TASK-0043/DEC-002.
- **DEC-005** — Still not verified by running. The development machine has no Docker, so this task,
  like TASK-0043, delivers configuration and is verified as configuration. The owner now has Claude
  on the VM, which is where a real deploy can be attempted and fixed.
