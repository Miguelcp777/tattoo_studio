# Task: Record what the studio does

## 1. Problem / requested change

The owner: "quiero registrar logs para poder monitorear toda la app … los tokens gastados, métricas
de tiempo y métricas útiles para monitorear el uso de la app". Choices: Supabase Postgres, with its
own login (not the master key). The administrator panel that reads these events is TASK-0055.
Evidence: INTENT.

## 2. Current behavior

No event is recorded anywhere. Provider responses carry token counts that nothing reads. Nothing
tells the owner what a generation cost, how long it took, whether it failed, or who ran it.
Evidence: OBSERVED.

## 3. Requirements

- **REQ-001** — Every paid provider call is recorded with provider, operation, model, duration,
  tokens, images and outcome, on success and on failure, and attributed to the account and job.
- **REQ-002** — Generations, uploads (and refusals), kept photos, erasures, consultation turns and
  sign-ins are recorded.
- **REQ-003** — Recording never delays or fails a request.
- **REQ-004** — No event holds an image; a refused sign-in holds no address and no account.
- **REQ-005** — A cost is computed only from configured prices, never guessed or accepted from the
  web tier.
- **REQ-006** — Erasing an account's data removes its identity and text from its events.
- **REQ-007** — Production keeps events in Supabase Postgres under a least-privilege login held
  only by the worker; a bad connection stops startup without revealing its password.
- **REQ-008** — Users are told what is recorded before they sign in.

## 4. Acceptance criteria

- **AC-001** — The store's SQL writes, reads, anonymises and purges events (on SQLite in tests).
- **AC-002** — A metered call records tokens, images, duration and cost; a failed one records an
  error and re-raises; an HTTP error status is an error; a transport error is named by type only.
- **AC-003** — A job, an upload, a refused upload and an erasure are recorded for the right account
  and job; a refused upload's event holds a reason and nothing else.
- **AC-004** — A store that is down drops and counts events and raises nothing; the buffer is bounded.
- **AC-005** — The worker's event route requires the token, takes the account from the header,
  drops unknown kinds and malformed operations, and prices calls itself.
- **AC-006** — The web tier reports Claude calls and consultation turns as the signed-in account,
  and a refused sign-in with no address and no account.
- **AC-007** — The SQL grants exactly usage, select/insert/delete and update of two columns.
- **AC-008** — Live: web → worker → store, with the account on every event of a signed-in request.

## 5. Decision log

- **DEC-001** — ADR-0024.
- **DEC-002** — The architecture test's egress rule now lists `psycopg` and allows `telemetry`,
  with the reason. Left out, the database connection would have been egress the scan cannot see.
- **DEC-003** — The web tier's account attribution is set in the route handler, not inside the
  guard: set inside `requireAccount` it did not reach back to the handler. Found only by the live
  run; the unit tests had passed.
- **DEC-004** — `report(event, null)` means "nobody". With `undefined` meaning "the current
  request", a refused sign-in was briefly attributed to whatever the context held.
