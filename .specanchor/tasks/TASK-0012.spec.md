# Task: Safe photo ingestion — media storage and the safety gate structure

Numbered outside 0001–0010, which the v0 plan reserves. This begins the photo-upload
capability the user asked for: converting a photograph of a pet or object into a
hyperrealistic tattoo design.

## 1. Problem / requested change

The product needs to accept a photograph and turn it into a tattoo design. Scope agreed
with the user: **pets and objects first, people later**, because a user can consent to
their own photograph being processed but cannot consent on behalf of a third person who
happens to be in it.

Nothing in the system can accept a photograph today. `image_to_image` exists but is
unreachable by construction, and neither `media` nor `safety` has any code.

## 2. Current behavior

- `SafetyClearance` lives in `generation/types.py` and cannot be constructed, so every
  image-conditioned path raises. Evidence: VERIFIED (TASK-0004).
- No `media` or `safety` code exists. Evidence: OBSERVED.
- The two modules declare a circular dependency on each other. Evidence: OBSERVED
  (FINDING-0003).
- Pillow 12.3.0 and cryptography 50.0.1 resolve. Evidence: VERIFIED (2026-09-19).

## 3. Desired behavior

A photograph can be screened, sanitised and stored safely, and a caller holding a
clearance can retrieve or delete it along with everything derived from it. The gate
exists and denies; what it cannot yet do is *pass* anything, because real moderation is
TASK-0013.

## 4. Scope

- `safety`: the `SafetyClearance` type moved here from `generation`, a `ModerationProvider`
  port, the gate structure, and a deny-by-default implementation.
- `media`: ingest with EXIF stripping, encryption at rest, a local filesystem backend,
  lineage recording, cascade deletion and retention expiry.
- `generation`: re-point at the relocated clearance type. No behaviour change.
- `platform`: Pillow and cryptography dependencies, storage and encryption settings.
- Resolving FINDING-0003 in the specs.

## 5. Out of scope

- Real moderation. The gate denies everything until TASK-0013 supplies a provider that
  can classify an image. A gate that cannot pass is useless but safe; a gate that passes
  without checking is neither.
- The OpenAI adapter and the portrait engine (TASK-0014).
- Consent records, age verification and the third-party-photograph question. Those belong
  to the people-photograph path, which this task deliberately does not open.
- Cloud object storage. The backend here is a local filesystem, which is honest about
  being a development implementation.
- Signed expiring URLs (MEDIA-INV-005). There is no HTTP surface to serve them from yet.

## 7. Requirements

- TASK-0012/REQ-001: The module dependency graph is acyclic. `safety` depends on
  `contracts` only; `media` depends on `safety` (FINDING-0003).
- TASK-0012/REQ-002: EXIF is stripped before any durable write, including GPS coordinates
  and device identifiers (MEDIA-INV-001, SEC-INV-002).
- TASK-0012/REQ-003: Stored bytes are encrypted at rest; reading the raw file yields no
  recoverable image (MEDIA-INV-002, SEC-INV-003).
- TASK-0012/REQ-004: `ingest_photo` refuses without a `SafetyClearance`, and nothing is
  written on refusal (MEDIA-INV-003, SEC-INV-007).
- TASK-0012/REQ-005: Every asset records its derivation lineage, and `delete_cascade`
  removes an asset and every descendant, at any depth (MEDIA-INV-004, SEC-INV-004).
- TASK-0012/REQ-006: Assets carry a retention class; photos and their derivatives expire,
  while designs containing no likeness do not (MEDIA-INV-006).
- TASK-0012/REQ-007: The gate denies on absence, error or provider unavailability, and
  cannot be configured to fall open in production (SAFETY-INV-001, SAFETY-INV-007).
- TASK-0012/REQ-008: A clearance is minted only by `safety`, only on an explicit pass, and
  is bound to the exact bytes screened — so it cannot be reused for a different image.
- TASK-0012/REQ-009: No image bytes, encryption key or storage path appears in any log
  record or error message (SEC-INV-008).

## 9. Design approach

**The gate runs before storage, which is what breaks the cycle.** `safety` receives bytes
and returns a verdict; it never reads from `media`. This matches SEC-INV-007 rather than
merely coexisting with it.

**A clearance is bound to a digest of the screened bytes.** Minting a token that says
"something passed" would let a caller screen a harmless image and then ingest a different
one. Binding it to the content makes that substitution fail.

**Encryption is real, not a placeholder.** AES-GCM with a key from settings. A development
backend that stored plaintext would make MEDIA-INV-002 a comment rather than a property,
and the module whose entire purpose is protecting sensitive images is the wrong place to
defer that.

**The gate denies everything for now.** That is deliberate: TASK-0013 supplies the
moderation provider. Shipping a gate that passes without checking, even temporarily, would
be the single most dangerous thing this project could do.

## 10. API / data / UI impact

## 13. Risks and rollback

- Pillow strips EXIF as a side effect of re-encoding, which also recompresses the image.
  For a photograph destined for stylisation that is acceptable, but it is lossy and should
  be stated rather than discovered.
- A local filesystem backend is not a production store. Retention sweeps, durability and
  residency all change when a real object store arrives.
- Key management is out of scope: the encryption key comes from settings, and rotating it
  would make existing assets unreadable. No rotation strategy exists.

Rollback is `git revert`; nothing consumes this yet.

- EV-003: Gate and clearance. 16 tests. Denies with no provider, denies when the provider

- EV-004: Cascade deletion. A three-level lineage is removed entirely with a receipt
  naming all three; an unrelated design survives, per its retention class.
- EV-005: Full suite. Worker 201 tests, contracts 70, TypeScript 66. ruff, ruff format and
  mypy strict clean in both Python packages. Guard --baseline exit 0 over 138 material
  files. Codegen reproducible. **337 tests total.**
- EV-006: Three defects were found by tests written to look for them, not by luck:
  1. **Pillow logs EXIF values at DEBUG**, including device make, model and the GPS
     pointer. An app running at DEBUG would have the imaging library write to the log the
     very identifiers this module strips from the file. PIL loggers are now silenced
     around every decode.
  2. **dataclasses.replace could forge a clearance.** The guard was a dataclass field, and
     replace copies fields, so a valid clearance could be cloned onto different bytes,
     defeating the binding completely. The guard is now a context flag set only inside
     mint_clearance, which a copy does not carry.
  3. **flash.spec.md declared a dependency on media**, which ARCH-INV-004 forbids and an
     existing test already blocked. The spec contradicted the invariant; the code did not.
