# Task: Repository skeleton, toolchain and CI

## 1. Problem / requested change

The repository contains specifications, the coverage guard and its configuration, and nothing
else. There is no way to install, lint, typecheck, test, build or run anything. Until that exists,
no acceptance criterion in any later task can be verified, and `.specanchor/README.md` cannot list
real test commands.

## 2. Current behavior

- Two commits: the SDD bootstrap and its evidence. Baseline at `e0d8493` reports 2 material files
  and an empty unmapped list. Evidence status: VERIFIED.
- No manifests, no application code, no CI. Evidence status: OBSERVED (directory listing).
- `pnpm` and `uv` are not installed on the development machine; `corepack` 0.32.0 is present.
  Evidence status: VERIFIED (`pnpm --version`, `uv --version`, `corepack --version`, 2026-09-19).

## 3. Desired behavior

Both runtimes installable, checkable and runnable, with CI enforcing the guard and the test suites
as separate checks. The skeleton is a shell only: no domain logic, no engines, no schemas. Those
belong to their own tasks.

## 4. Scope

- pnpm workspace: root `package.json`, `pnpm-workspace.yaml`, `tsconfig.base.json`.
- `apps/web`: Next.js application shell that builds and serves one placeholder route.
- `services/worker`: `pyproject.toml` managed by uv, FastAPI application shell under
  `services/worker/app/` with typed settings and a health endpoint.
- Lint, format, typecheck and test wired for both runtimes, each with at least one real test.
- GitHub Actions workflow running the guard, the TypeScript suite and the Python suite as separate
  jobs.
- Correcting `.specanchor/module-map.json` to the toolchain files actually created.
- Filling in the real commands in `.specanchor/README.md` and `platform.spec.md`.

## 5. Out of scope

- Any contract schema (TASK-0002).
- Any engine, provider adapter, queue, storage or moderation code.
- Authentication, database, deployment configuration.
- Creating package shells for modules whose tasks have not started — those directories stay absent
  rather than being filled with placeholders.

## 9. Design approach

Minimal shells, real checks. The value of this task is that every later task has somewhere to put
code and something to run against it — not that the shells do anything.

pnpm and uv are installed for the current user only; both installations are environment setup and
are recorded in the evidence ledger. The intended route for pnpm was `corepack`, which needs no
global npm install — it failed with EPERM because it writes shims into the Node installation
directory, so the documented fallback was used instead. See EV-001.

Settings use `pydantic-settings`, so REQ-006 is a property of the settings model rather than
hand-written validation.

## 10. API / data / UI impact

One placeholder web route and one worker health endpoint. Neither is a product surface and neither
carries a contract; they exist so the build and the test suites have a target.

## 13. Risks and rollback

- pnpm via corepack may require elevated permissions on Windows to write shims. Fallback is a
  user-scoped npm install of pnpm. Either way the workspace layout is unaffected.
- uv installation may be blocked by policy. Fallback is `pip install --user uv`, and failing that
  the Python toolchain decision returns to the user.
- The CI workflow cannot be executed locally. It will be syntactically validated and its logic
  reviewed, but recorded as NOT_RUN until a remote exists. This is a real limit and must not be
  reported as passing.

Rollback is `git revert` of a single commit; nothing else depends on this yet.

## 16. Evidence ledger

- EV-001: Toolchain installation.
  `corepack enable pnpm` **failed** with EPERM, needing to write into the Node installation
  directory under Program Files. Fallback used: `npm install -g pnpm`, which installs into the
  user-scoped npm prefix under the user profile, giving pnpm 12.4.2.
  `python -m pip install --user uv` gave uv 0.12.17. Nothing was installed with elevated
  permissions and nothing was written outside the user profile.
- EV-002: TypeScript. `pnpm install` exit 0 (clean, no warnings, after allowing the single
  `esbuild` install script). `pnpm lint` exit 0. `pnpm typecheck` exit 0.
  `pnpm test` exit 0, 4 tests passed. `pnpm --filter web build` exit 0, no warnings.
  Strict mode confirmed effective after Next.js rewrote `apps/web/tsconfig.json`:
  `tsc --showConfig` reports `strict: true` and `noUncheckedIndexedAccess: true`.
- EV-003: Python. `uv sync` exit 0. `uv run ruff check .` exit 0. `uv run ruff format --check .`
  exit 0, 6 files. `uv run mypy .` exit 0, strict, 6 source files. `uv run pytest` exit 0,
  8 tests passed.
- EV-004: Settings failure path. Covered by `app/tests/test_settings.py`. Asserts that a missing
  required key raises and names `environment`; that a malformed value is reported by key with the
  value absent from the message; and that the entrypoint exits 1 and writes to stderr.
- EV-005: Coverage. `--baseline` initially **failed** with five unmapped root configuration files
  (`.npmrc`, `.prettierignore`, `.prettierrc.json`, `eslint.config.mjs`,
  `services/worker/.python-version`). Module map corrected; `--baseline` then exit 0 with
  27 material files and an empty unmapped list.
- EV-006: CI. `.github/workflows/ci.yml` parses as valid YAML and declares three independent jobs
  (`spec-coverage`, `typescript`, `python`) with 4, 8 and 7 steps. **The workflow has never
  executed**: there is no remote. Action versions, the pnpm and uv setup steps, and Linux
