# Task: Designs belong to the account, not to the browser

## 1. Problem / requested change

The owner, after the login shipped: "sigue con TASK-0046". ADR-0021 left it explicit that designs
were still owned by the anonymous studio session, and that signing in as yourself on another device
shows nothing. Evidence: INTENT.

## 2. Current behavior

- The worker scopes everything it stores by an opaque `owner` string: `assets.owner`,
  `jobs.owner`, `design_vector.owner`, `consent.owner`. The scoping itself is complete and already
  tested for cross-owner isolation. Evidence: OBSERVED (`services/worker/app/studio.py`,
  `services/worker/jobs/queue.py`).
- The web tier fills that string with `current.state.sessionId`, the id of the in-memory
  consultation session, which lives in a `inkcraft` cookie for 24 hours and is unrelated to the
  account. Evidence: OBSERVED (nine call sites in `api/generate` and `api/media`).
- Consequence: the same person on a second device is a different owner. Their history is empty,
  their media ids resolve to nothing, and a resized design cannot find its vector master.
  Evidence: OBSERVED.
- Reading stored work requires an active consultation session. `session(request)` throws 401 when
  the `inkcraft` cookie is absent, before the request reaches the worker, and the page only asks
  for history inside `if (data.session)`. Evidence: OBSERVED (`api/generate/route.ts:96`,
  `app/page.tsx:159`).
- Deleting your work writes the owner into a `revoked` table and every later request for that owner
  is refused permanently. With a session id that is harmless — the browser simply starts a new
  session. Evidence: OBSERVED (`studio.py:229,264,664`).

## 3. Requirements

- **REQ-001** — Stored work — media, jobs, history and the vector master — belongs to the account.
  The same account on another device sees the same work.
- **REQ-002** — One account's work is unreachable by any other account, by id or by listing.
- **REQ-003** — Reading your own work does not require a consultation in progress.
- **REQ-004** — Deleting your work removes it and leaves the account able to keep working. Deletion
  is not a lockout.
- **REQ-005** — Work generated from a request that began before a deletion is not written after it.
  A deletion that lands mid-generation leaves nothing behind.
- **REQ-006** — The web tier tells the worker whose work this is in a header named for what it
  carries, and the worker refuses anything that is not a well-formed account id.
- **REQ-007** — The consultation itself stays where it is: in the browser's session. Signing in on
  a second device shows your designs, not a half-finished conversation from the first.

## 4. Non-goals

- **Durability.** Retention is unchanged: media expire after 24 hours and history covers 24 hours,
  so "your designs on another device" means the last day's. Durable storage is TASK-0047.
- **Migration of existing work.** Assets owned by old session ids become unreachable and expire on
  the normal retention schedule. The deployment has one account and a day's worth of demo output;
  writing a migration would cost more than it preserves.
- **Sharing between accounts.** There is no notion of one account seeing another's work.

## 5. Acceptance criteria

- **AC-001** — The worker receives the account id as the owner on every call: upload, media read,
  job submission, status, history and deletion.
- **AC-002** — Two sessions of the same account share one history; a second account with the same
  session cookie sees an empty history and cannot read the first account's media id.
- **AC-003** — History and job status answer 200 for an account with no consultation in progress.
- **AC-004** — After deletion, the same account can upload and generate again; nothing from before
  the deletion is readable.
- **AC-005** — A deletion that lands between the start of a generation and its storage step makes
  the job fail, and no asset row survives for that owner.
- **AC-006** — The worker refuses a call whose owner header is missing or not a UUID.
- **AC-007** — The decision the page opens with asks for the account's designs when there is no
  consultation, restores the conversation when there is one, and never replaces a design that is
  still being generated.

## 6. Decision log

- **DEC-001** — The consultation session stays in the browser and keeps its cookie. Only ownership
  of stored work moves. Moving the conversation to the account would mean two devices editing one
  consultation, which is a different feature with its own concurrency problem (REQ-007).
- **DEC-002** — Permanent revocation is replaced by a deletion watermark: `deleted(owner, at)`.
  `active()` refused a deleted owner forever, which was right for a throwaway session id and is a
  lockout for a stable account id. What that check actually protected is narrower — a job that
  started before a deletion must not register assets after it — and a watermark compared against
  the moment the work started protects exactly that, and nothing more (REQ-004, REQ-005).
- **DEC-003** — `X-Session-Id` becomes `X-Owner-Id`. A header named for a session while carrying an
  account id is the kind of lie the next reader acts on. The worker validates a UUID, which is what
  Supabase issues.
- **DEC-004** — Read-only routes stop requiring the consultation session rather than creating one
  for them. A history read should not mint a consultation as a side effect.
- **DEC-005** — The page's opening branch moved into `lib/opening.ts`. Left inside the effect it
  would have been the one part of this task with no test at all, and it is exactly the part that
  decides whether a signed-in device sees its designs or an empty studio. The wiring into the DOM
  is still unexecuted and recorded as such.

## 7. Verification plan

- Worker: cross-account isolation, deletion-then-reuse, the mid-generation deletion, and the header
  contract, in `services/worker/app/tests/test_studio.py`.
- Web: the owner passed to the worker is the account id and not the session id, and the read-only
  routes answer without a consultation cookie.
- Live: sign in on a second browser profile and see the same history.
