# Task: Moderation provider — the gate learns to pass

## 1. Problem / requested change

TASK-0012 built a gate that denies everything, because no moderation provider existed.
That is safe and useless. This task supplies the provider, so a photograph of a pet or an
object can pass while a photograph containing a person, or explicit content, is refused.

## 2. Current behavior

- `InputGate` denies every input with `no_moderation_provider`. Evidence: VERIFIED
  (TASK-0012, 16 gate tests).
- ARCH-INV-001 permits outbound model calls from `generation` alone, and an architectural
  test enforces it by scanning imports. Evidence: VERIFIED (TASK-0004).
- `OPENAI_API_KEY` is present in the developer's environment. Evidence: VERIFIED
  (2026-09-19, length checked without reading the value).
- OpenAI's Responses API accepts `input_image` as a Base64 data URL at
  `POST https://api.openai.com/v1/responses` with `Authorization: Bearer`. Evidence:
  OBSERVED (OpenAI documentation, 2026-09-19).

## 3. Desired behavior

An uploaded pet or object photograph passes the gate and yields a clearance. A photograph
containing a person is refused, as is explicit content. Any uncertainty, malformed
response or provider failure is a refusal.

## 4. Scope

- `safety`: an OpenAI vision moderation provider, its HTTP transport, and wiring.
- `architecture`: amend ARCH-INV-001 so `safety` may reach its own provider.
- `platform`: OpenAI settings, and the architectural test's egress allowlist.
- Live verification against real images.

## 5. Out of scope

- The portrait engine that turns the photograph into a tattoo (TASK-0014).
- `screen_output`, `screen_brief`, consent records and age verification.
- People photographs as a product capability. The gate refuses them; opening that path is
  a separate decision with its own consent design.

## 9. Design approach

**ARCH-INV-001 is amended, not circumvented.** The invariant was written when the only
outbound calls anyone imagined were image generation. Moderation is a different concern
and belongs to `safety`.

Routing it through `generation` was considered and rejected for a specific reason: it
would make the gate's integrity depend on the availability and correctness of the module
the gate exists to constrain. A bug or outage in `generation` would then be able to
disable moderation, which inverts the relationship. `safety` owning its own egress keeps
the gate independent.

The amended invariant remains narrow: `generation` may call image models, `safety` may
call its moderation provider, and no other module may call anything. The test enforces
both halves and still proves the allowlist is non-vacuous.

**One vision call answers both questions.** The model is asked to report whether the image
contains a person and whether it is explicit, as strict JSON. Two calls would cost twice
and could disagree with each other.

**Everything ambiguous is a refusal.** A parse failure, a missing field, a non-boolean
value, an HTTP error or a timeout all mean the same thing: nothing was verified. The gate
already treats a raising provider as a denial; this task makes sure the provider raises
rather than guessing.

## 13. Risks and rollback

- The Responses API shape is taken from documentation. Request construction and response
  parsing are tested against a scripted transport, which proves they handle what the docs
  describe, not that the API matches. AC-007 is what closes that gap.
- Vision classification accuracy is unmeasured. A drawing of a person, a statue, a
  reflection or a person partially in frame are all cases nobody has checked.
- Moderation cost is per upload and unbudgeted.

Rollback is `git revert`; the gate returns to denying everything, which is safe.

## 16. Evidence ledger

Windows 11, 2026-09-19.

- EV-001: Architecture. `EGRESS_ALLOWED` widened to `generation` and `safety`; the
  non-vacuous check passes for both, because `safety/http.py` imports a real client. Any
  other module importing one still fails the scan.
- EV-002: Classification. 46 provider tests. Reads clean, person and explicit verdicts in
  both plain and code-fenced JSON, and through both the convenience and structured
  response shapes. Raises on 7 HTTP error codes, a transport failure, a non-JSON body,
  6 response shapes carrying no usable text, and 9 malformed verdicts including string
  booleans, numeric booleans, nulls and missing fields.
- EV-003: Leakage. The key is absent from captured logs and from the string and repr of
  every raised error across three failure modes. A transport message quoting a URL with a
  token is not echoed.
- EV-004: **Live, against the real OpenAI API.** Three images generated with fal and
  screened: a golden retriever **passed**, a pocket watch **passed**, a photograph of a
  woman was **refused with `contains_person`**. All three behaved as specified.
- EV-005: Full suite. Worker 247 tests. The gate suite is 62 (16 structural, 46 provider).

**Not measured:** accuracy. Three synthetic images is a smoke test. A drawing or statue of
a person, a reflection, a partial figure, a background crowd and an owner's hand in a pet
photograph are all unchecked, and the prompt deliberately biases toward refusal when
unsure, which nothing quantifies.
