# Task: Keep a photo from the camera as a version

## 1. Problem / requested change

The owner, using the camera try-on on a phone: "necesito un botón para que me haga foto y me la
guarde en la app como una propuesta más de diseño". Evidence: INTENT.

## 2. Current behavior

- `/probar` has no shutter. ADR-0019 promises that no frame leaves the device, and
  `probar/no-upload.test.ts` fails the suite if the page gains any way to send. Evidence: OBSERVED.
- Versions are succeeded jobs in the owner's history; the only way to create one is to queue a
  generation. Evidence: OBSERVED (`jobs/queue.py`).
- The link into the try-on carries only the design's asset id, not the version it came from.
  Evidence: OBSERVED (`TattooPreviewModal.tsx`).

## 3. Requirements

- **REQ-001** — On the try-on, a shutter takes one photograph of the camera view with the design on
  it. Taking it sends nothing.
- **REQ-002** — The client can keep it or discard it. Keeping requires confirming they are an adult
  and consenting to it being stored; without both nothing is sent.
- **REQ-003** — A kept photo becomes a new version of the same design, listed with the others as
  "Foto con la cámara", and opens showing the photograph.
- **REQ-004** — A kept photo takes the own-photo path: safety gate with own-body consent, EXIF
  stripped, encrypted, counted, erased by "delete my data".
- **REQ-005** — A kept photo never reaches an image model, including when a change is asked from its
  version.
- **REQ-006** — The live stream still never leaves the device, and the source scan says so.

## 4. Acceptance criteria

- **AC-001** — `snapshot` composes one frame at up to 1440 px with no request; the page calls it
  from one place.
- **AC-002** — Without adult and consent, the page, the route and the worker each refuse, and
  nothing is stored.
- **AC-003** — A kept photo's version equals its parent in master, stencil, PDF, size and mockup,
  and adds `capture.photo`; history lists it first.
- **AC-004** — A photo refused by moderation stores nothing; a retried save stores and screens once.
- **AC-005** — Deleting the account's data removes the kept photo and its version.
- **AC-006** — An edit from the photo's version succeeds and none of the model's inputs is the photo.
- **AC-007** — The source scan: page, compositor and blend have no egress and no serialisation;
  `lib/capture.ts` has one `fetch`, to `/api/captures`, no timer or loop, no recorder.
- **AC-008** — Live: shutter, review, consent gating, save, the version in the studio, and deletion.

## 5. Decision log

- **DEC-001** — ADR-0022 amends ADR-0019 narrowly rather than replacing it. The exception is one
  photograph, two explicit acts, adult consent, one module, one route.
- **DEC-002** — The photo is stored through `Studio.ingest` as a `body` asset instead of a new
  storage path, so every own-photo invariant applies without being re-implemented.
- **DEC-003** — The version copies its parent's result and adds `capture`. The contract gains an
  optional field rather than a new artifact kind, so the studio, history and edits need no new
  branch beyond what to display.
- **DEC-004** — `capture.photo` has its own definition admitting JPEG, because own-body photos are
  stored as JPEG; the shared `asset` type is left alone so masters and stencils stay PNG/SVG/PDF.
- **DEC-005** — The review scrolls into view with an instant jump. A smooth scroll never moved in
  the test browser, and a shutter that appears to do nothing is the failure to avoid.
