# Task: Try the tattoo on with the camera, without a frame leaving the phone

## 1. Problem / requested change

Phase 1.3 of the competitive plan, chosen by the owner over the other Phase 1 items. InkHunter and
Tatship both offer a live camera try-on; we offered none. Evidence: INTENT.

## 2. Current behavior

- A client sees their design only as the studio's rendered mockup on a generated plate. Evidence:
  OBSERVED.
- The app is a plain web page: no manifest, no service worker, not installable. Evidence: OBSERVED.

## 7. Requirements

- **REQ-001** — A page that opens the device camera and draws the client's design onto the live
  frame, movable by dragging and adjustable in size and rotation.
- **REQ-002** — The ink treatment is a port of the worker's composite: multiply, surface
  attenuation read from the frame (ADR-0014) and the fresh-ink ring (TASK-0031). The artwork's
  geometry is never displaced (MOCKUP-INV-001).
- **REQ-003** — No camera frame leaves the device. The page's only request is the GET for the
  client's own design, by a validated asset id.
- **REQ-004** — The studio is installable: manifest, icons and an app-shell service worker that
  never caches or intercepts `/api/`.
- **REQ-005** — The page carries the visualization disclaimer (WEB-INV-003) and says plainly that
  the camera stays on the device.
- **REQ-006** — Camera refusal, absence and failure each get their own message and a retry.

## 8. Acceptance criteria

- **AC-001** — Unit: the attenuation follows the frame's light, is bounded, and survives a black
  frame; ink multiplies into skin; bare artwork changes nothing; a transparent design changes
  nothing.
- **AC-002** — Unit: the plain multiply changes exactly the columns the design darkens and no
  others (geometry is not displaced).
- **AC-003** — Unit: skin beside a stroke reddens more than skin far from it and more than the
  stroke itself (the ring surrounds the ink).
- **AC-004** — Source scan: page, compositor and blend contain no egress API; the page's only image
  source is `/api/media?id=${id}`; the id is validated as 32 hex.
- **AC-005** — Live: the real compositor, called against a camera substitute, draws the design onto
  the frame with ink darker than the skin and a warmer ring beside it.
- **AC-006** — The production build succeeds and serves the manifest, the icons and the worker.
- **AC-007** — A `getUserMedia` refusal classifies as `denied` and any other failure as `failed`;
  a browser with no camera API classifies as `unsupported`.

## 15. Decision log

- **DEC-001** — ADR-0019: everything on the device, the blend ported rather than reinvented, and
  the no-egress promise pinned by a source-scan test.
- **DEC-002** — No body segmentation in this step. MediaPipe would keep the privacy property but
  adds a multi-megabyte model and a WASM runtime, and cannot be validated here. Consequence: the
  design follows the finger, not the limb, and ink placed off the body lands on the background.
  Recorded in ADR-0019 rather than hidden.
- **DEC-003** — The per-frame composite lives in `lib/try-on.ts`, not in the page. The page owns the
  camera and the loop. This is what made AC-005 possible: with no camera and no visible window,
  `requestAnimationFrame` never fires, so the frame had to be drivable on its own.
- **DEC-004** — The page exposes `window.__tryOnPaint` for that check. It is a read-only handle to
  the same function the loop calls, added deliberately rather than duplicating the composite in a
  test double, which would have verified a copy instead of the product.
- **DEC-005a** — The failure classification lives in `try-on.ts` as `cameraFailure` /
  `cameraAvailable` rather than inline in the page, so REQ-006 is verified by a test instead of by
  a traceability row claiming "partial". A real refusal on a real device stays NOT_RUN.
- **DEC-005** — The service worker registers in production only. In development Next rewrites
  modules on every edit, and a worker holding copies turns an edit into a stale-asset hunt.

## 16. Evidence ledger

- **ev-001** — Verification run, 2026-09-28. Status: VERIFIED by execution.
  - TypeScript: `pnpm lint` clean, `pnpm -r typecheck` clean, tests 107 + 86 + **55** (web 41
    before: 14 added).
  - `skin-blend.test.ts` 9 passed (AC-001..003); `probar/no-upload.test.ts` 3 passed (AC-004);
    `try-on.test.ts` 2 passed (AC-007).
- **ev-002** — Production build, 2026-09-28: `next build` succeeded; `/probar` is a static route at
  3.55 kB; `/manifest.webmanifest` is generated. Served from `next start`: the manifest returns the
  expected JSON, `/sw.js` returns 200 `application/javascript`, `/icons/icon-192.png` returns 200.
  Status: VERIFIED (AC-006).
- **ev-003** — Live check in the browser pane against the dev server, 2026-09-28. A design was
  uploaded into a real session, the page loaded it, `getUserMedia` was replaced with a canvas
  `captureStream` of a lit synthetic limb, and the page's own compositor was called for one frame.
  It returned true and produced a 480x640 canvas: backdrop unchanged at rgb(75,74,77); the darkest
  point on the limb at luminance 74 against skin at 161 (ink darker than skin); warmth beside the
  ink 64 against 61 well away from it (the ring surrounds the stroke). Status: VERIFIED (AC-005).
- **NOT_RUN** — **A real camera on a real phone, iOS and Android, in good and bad light.** The
  development environment has no camera, and the browser pane's window is never visible, so
  `requestAnimationFrame` does not fire and the animation loop itself is unexercised. Only the
  per-frame composite is proven.
- **NOT_RUN** — **Service worker registration and the offline shell.** The embedded browser refuses
  to fetch the worker script ("An unknown error occurred when fetching the script") although the
  same URL returns 200 over HTTP. The registration is wrapped in a catch, so a browser that refuses
  it simply gets no offline cache; the page was confirmed to work with no worker controlling it.
